Keeping requests moving.

A clock-based C++ simulation that balances incoming web requests across a changing pool of servers.

01 / From arrival to completion

Requests carry a source IP, destination IP, duration and a processing (P) or streaming (S) category. Accepted requests wait in a first-in, first-out queue. Idle servers take the oldest waiting request.

At initialization, the queue is filled with 100 accepted requests per starting server. Every cycle samples new arrivals, filters their source addresses, considers scaling, assigns available work, then advances each server by one cycle. Completed work is counted; a retired server is deleted once its current job finishes. The simulation ends at the requested cycle with any unfinished work reported.

02 / Capacity changes without losing work

When the queue exceeds 80 × active servers, the controller adds one server. Below 50 × active servers, it retires one, keeping at least one active. It waits the configured cooldown between changes. Exact threshold equality causes no scaling. The default cooldown is 100 cycles, and allocated capacity is capped at 200 servers.

Idle servers retire first. A busy retiring server stops accepting work and finishes its current request before deletion. The queue band is a target rather than a guarantee: traffic bursts, cooldowns and capacity limits can temporarily put the queue outside it.

04 / Configuration and observability

Edit config.txt to change arrival probability, burst size, task duration range, server limits, cooldown, blocked source range and random seed. --interactive asks for the starting server count and duration. Quiet mode writes beginning/end summaries; verbose mode adds arrival, blocking, assignment, completion and scaling events. Console color is optional; the log is plain text.
